## 0. 一句话结论

**驱动不了狗，不是网络问题、不是固件版本、不是 SDK 坏了，是"启动 bridge 的方式"和现场约定不一致。**

我照官方 README 手搓了 `ros2 launch uniubi_motion_bridge ...`，而现场的正确入口是一个 6 行的 wrapper（`bridge.bash`）+ 用户级 systemd 服务 + 一份独立 YAML。四处参数差异叠加，导致 DDS 发现不稳定、RPC 全部超时。

## 2. 根因：四处差异

官方 `~/robot_tools/uniubi_motion/bridge.bash`：

```bash
#!/usr/bin/env bash
set -e
here=$(dirname "$(realpath "$0")")
source "$here/dog_env.bash"
exec ros2 run uniubi_motion_bridge uniubi_motion_bridge_node --ros-args \
  --params-file "$here/motion_bridge.yaml" \
  -p robot_service_name:=/robotServer \
  -p auto_connect:=false -p cmd_vel_topic:=/cmd_vel -p cmd_vel_timeout_ms:=450
```

| # | 项目 | 官方 | 我手动 `ros2 launch` | 后果 |
|---|---|---|---|---|
| ① | **DDS 配置** | `source dog_env.bash`，含 `<Peer address="192.168.100.114"/>` | 无 Peers | 退回纯多播发现 → DDS 学到的对端地址时对时错 → **话题能收、RPC 必超时** |
| ② | `auto_connect` | `false`（按需连接） | 默认 `true` | 启动即做 RPC 就绪检查 → 立刻触发 `getMotionCapabilities` 超时 |
| ③ | `robot_service_name` | `/robotServer` | 未指定（用默认值） | 服务名对不上 → RPC 找不到服务端 |
| ④ | 参数来源 | `motion_bridge.yaml` | 命令行只给 `device_id` | 缺 lease、各 rate 等参数 |

**①是主因，但四条任意一条都足以让 RPC 死。** 这也解释了那个最迷惑人的现象：

> 话题能收到数据，RPC 却全超时。

因为话题是广播式的（不需要对方回包到你），而 RPC 必须按服务名找到 `/robotServer` 并把应答**单播回你**。回程地址学错了，就永远等不到。

### 现场的 DDS 配置（原文，务必保留）

`~/robot_tools/uniubi_motion/dog_env.bash`：

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=42 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp ROS_LOCALHOST_ONLY=0
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><General><Interfaces><NetworkInterface name="wlP1p1s0"/></Interfaces><AllowMulticast>true</AllowMulticast></General><Discovery><Peers><Peer address="192.168.100.114"/></Peers><ParticipantIndex>auto</ParticipantIndex></Discovery></Domain></CycloneDDS>'
```

三个要点：

- **`Peers` 里有狗的 IP** —— 这是稳定性的关键，把发现钉在单播上
- 属性是**小写 `address`**（上游文档写成 `Address`，可能不被识别）
- `Domain Id="any"`，配合 `ROS_DOMAIN_ID=42` 生效

## 3. 正确启动方式（唯一）

### 3.1 正式

```bash
systemctl --user start uniubi-motion-bridge     # 域 42，SDK 桥接
systemctl --user start uniubi-cmd-vel-link      # 跨域：域 0 的 /cmd_vel → 域 42
```

用户级 unit 文件位置：

```
~/.config/systemd/user/uniubi-motion-bridge.service
~/.config/systemd/user/uniubi-cmd-vel-link.service
```

### 3.2 前台调试（能看日志）

```bash
bash ~/robot_tools/uniubi_motion/bridge.bash
```

### 3.3 禁止

```bash
# ✗ 会绕过 dog_env.bash，注定 RPC 不通
ros2 launch uniubi_motion_bridge motion_bridge.launch.py device_id:=...
```

### 3.4 环境加载顺序（容易搞错）

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
source ~/robot_tools/uniubi_motion/dog_env.bash   # 它负责域 42 + Peers
# 之后不要再 source 其它会覆盖 LD_LIBRARY_PATH / ROS_DOMAIN_ID 的脚本
```

### 3.5 两个域，别混

| 侧 | `ROS_DOMAIN_ID` | 内容 |
|---|---|---|
| 导航 / 画线 / 循线 | **0** | Nav2、`walk.py`、RViz、`/cmd_vel`（源） |
| SDK 桥接 | **42** | `uniubi-motion-bridge`、`/motion/*`、`/cmd_vel`（目标） |

`uniubi-cmd-vel-link` 负责把域 0 的 `/cmd_vel` 转发到域 42。

## 4. 常用指令速查

### 4.1 官方入口（`~/robot_tools/office4_route/`）

| 脚本 | 作用 | 依赖 |
|---|---|---|
| `locate_at_start.bash` | 恢复定位（Office4 + 全零初值） | 雷达、FAST-LIO2、localizer |
| `start.bash` | 起 RViz 画线界面 | NoMachine 桌面 |
| `stand.bash` | 取权 + 进入零速 walking | 仅 SDK 桥接 |
| `walk.bash` | 跟线执行；`--resume` 从当前位置续走 | 已保存路线 + 定位 |

`stand.bash` 实际做的事（剥掉 ROS 皮就是这两句）：

```python
call('/motion/acquire_control', Trigger)                                  # client->startControl()
call('/motion/start_action', StartMotionAction{action:'walking',
     params_json:'{"lineVelocityX":0,"lineVelocityY":0,"velocity":0}'})   # client->startAction()
```

### 4.2 直接发速度（域 42）

```bash
source ~/robot_tools/uniubi_motion/dog_env.bash

# 直走约 1 米（0.15 m/s × 6.65 s）
ros2 topic pub -r 20 --times 133 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.15, y: 0.0}, angular: {z: 0.0}}'

# 原地左转约 90°（0.30 rad/s × 5.2 s）
ros2 topic pub -r 20 --times 104 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.0, y: 0.0}, angular: {z: 0.30}}'
```

### 4.3 交还控制权 / 急停接管

```bash
# 正常交还
ros2 service call /motion/release_control std_srvs/srv/Trigger '{}'

# 现场急停：直接按遥控器 LB+RB
# 强制接管：长按遥控器 M 键，直到听到"遥控器已连接"
```

> `stand.bash` 之后狗处于"零速 walking 且控制权被程序占用"，此时遥控器接不回来。

### 4.4 速度语义（必须记住）

| 字段 | 含义 | 单位 |
|---|---|---|
| `lineVelocityX` / `linear.x` | 前后，正=前 | m/s |
| `lineVelocityY` / `linear.y` | 横移，正=左 | m/s |
| `velocity` / `angular.z` | 转向，正=左 | rad/s |

- **速度是"持续生效的参数"，不是一次性命令**：一直生效到被覆盖或超时清零
- `set_action_params` 是**全量重写**，未传字段归 0 → 三个字段都显式给
- bridge 的 `cmd_vel_timeout_ms=450`：停发约半秒后自动清零速度
- 没有"走 1 米""转 90 度"这种指令，距离/角度只能靠「速度×时间」或里程计闭环

## 7. 排障流程规则（这次最大的收获）

### 7.1 信息源排序：现场 > 文档

我这次最根本的错误，是把**上游官方文档**当成了**这台机器的真相**。

> 一行 wrapper 的权重，超过几千行文档。

规则：

1. **先要现场产物，再读文档**：`history`、`*.bash`、`systemctl --user cat`、`ps -ef`、`cat` 配置。四样齐了再开口猜。
2. **不自己发明配置**。缺配置文件就要原始文件。我自制的 `dds-wifi.xml`（看起来很像）制造了虚假进展。
3. 文档描述的是**上游组件的行为**；现场跑的是**别人组装过的系统**。要控制的是后者。

### 7.2 "别人能跑通"是 diff 题，不是证明题

不是"他没接网线也能跑，所以网络不是问题"，而是：

> 把他的调用方式逐项列出来 —— 环境、参数、启动方式、作用域 —— 和我的一行行对比，缺哪补哪。

我当时问的是"狗重启过吗""是不是接了网线"（问**状态**），该问的是"**上次成功时你敲的那几条命令，原样贴给我**"（问**调用**）。

### 7.3 查不到服务时，先换作用域

`systemctl status uniubi-motion-bridge` → `Unit could not be found`。
我据此排除了"后台服务在跑"这个正确假设 —— 但它是**用户级**服务：

```bash
systemctl --user status uniubi-motion-bridge
systemctl --user list-units --type=service
journalctl -b _SYSTEMD_USER_UNIT=office4-route.service -n 120 --no-pager
```

### 7.4 一次只改一个变量

中途同时动过：网卡限制、多播开关、手动 launch、超时重试。结果后面对不上账，也无法归因。

### 7.5 反复修不好时，质疑前提

我在这条错误路径上做过很多**质量不差但对象错了**的分析：多播注入测试、61 个 DDS 域扫描、端口扫描、TCP 抓包方案。

真正让问题破局的是自己那句话：

> 之前的结论可能已经过时了，能不能再试试 office4 里的链路方法？

**当一个问题反复修不好，该质疑的是前提，不是细节。**
